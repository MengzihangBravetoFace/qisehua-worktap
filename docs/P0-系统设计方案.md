## 一、需求分析与 P0 边界

### 1.1 核心理念

以**个人（Person）**和**组织（Organization）**为两类主体节点，主体之间通过**关系（Relationship）**连接，形成一张可查询、可展示的主体网络。

### 1.2 P0 必做能力（7 项）

| # | 能力 | 说明 |
|---|------|------|
| 1 | 统一主体模型 | 个人与组织共用一张表，`type` 字段区分 |
| 2 | 核心字段模板 | 个人/组织各自一套可配置的核心字段 |
| 3 | 主体关系建立 | 手动创建主体间关系 |
| 4 | 数据上传 | 支持 Excel 和聊天记录（文本）上传 |
| 5 | AI 提取 | 调用模型 API 识别、提取主体与关系 |
| 6 | 去重匹配 | 对 AI 提取结果与库内主体进行去重 |
| 7 | 人工审核入库 | 审核通过后才写入正式主体表 |
| 8 | 主体画像展示 | 展示单个主体的完整信息与关系网络 |

### 1.3 P0 明确不做（防止需求蔓延）

- ❌ 不做用户/权限/多租户（单管理员使用）
- ❌ 不做自定义关系类型的动态管理（P0 内置枚举）
- ❌ 不引入图数据库（PostgreSQL 关系表 + JSONB 足够）
- ❌ 不做 AI 问答/对话（仅结构化提取）
- ❌ 不做历史版本/变更审计（仅保留创建/更新时间）
- ❌ 不做批量导入向导的字段拖拽映射（P0 用固定列名模板）

### 1.4 关于技术选型的判断

用户给定的技术栈合理，无重大问题：

- **PostgreSQL**：用 `JSONB` 存储扩展字段，用关系表存主体间连接，P0 阶段不需要 Neo4j。若后续关系查询深度超过 3 层再评估迁移。
- **FastAPI + Pydantic**：天然适合做结构化数据校验，与 AI 输出的 JSON 契约契合。
- **React + TS + Vite**：标准组合，无异议。

## 二、系统整体架构

### 2.1 分层架构

```
┌─────────────────────────────────────────────────────────┐
│                     前端 (React + TS + Vite)              │
│  ┌───────────┐  ┌───────────┐  ┌───────────┐  ┌────────┐│
│  │ 数据上传页 │  │ 审核工作台 │  │ 主体画像页 │  │图谱展示││
│  └─────┬─────┘  └─────┬─────┘  └─────┬─────┘  └───┬────┘│
└────────┼──────────────┼──────────────┼────────────┼─────┘
         │              │              │            │
         ▼              ▼              ▼            ▼
┌─────────────────────────────────────────────────────────┐
│                    后端 (FastAPI + Pydantic)              │
│                                                           │
│  ┌──────────┐ ┌───────────┐ ┌──────────┐ ┌────────────┐ │
│  │ 文件解析  │ │ AI 提取服务 │ │ 去重匹配  │ │  审核入库   │ │
│  └──────────┘ └───────────┘ └──────────┘ └────────────┘ │
│                                                           │
│  ┌─────────────────────────────────────────────────────┐ │
│  │              数据访问层 (SQLAlchemy 2.x)             │ │
│  └─────────────────────────────────────────────────────┘ │
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────┐
│                  PostgreSQL 15+                          │
│   subjects / relationships / extraction_results / ...   │
└───────────────────────────┬─────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────┐
│              AI 模型 API（结构化信息提取）                │
│   输入：文本  输出：符合 JSON Schema 的主体+关系数组      │
└─────────────────────────────────────────────────────────┘
```

### 2.2 核心数据流（上传 → 入库）

```
用户上传 Excel/聊天记录
        │
        ▼
  [文件解析] → 文本内容
        │
        ▼
  [AI 提取] → 候选主体[] + 候选关系[]
        │
        ▼
  [去重匹配] → 标注每个候选是"新建"还是"匹配已有主体ID"
        │
        ▼
  [人工审核] → 通过 / 修改 / 拒绝
        │
        ▼
  [审核通过] → 写入 subjects + relationships 正式表
```

### 2.3 设计原则（来自经验教训）

1. **实体类型强约束**：主体类型只用 `person | org` 两个枚举值，关系类型用内置枚举，不在 P0 开放自定义。
2. **全链路 JSON 契约一致**：AI 提取输出的 Schema、后端 Pydantic 模型、前端 TS 类型三者必须完全一致，字段名统一用 `snake_case`。
3. **不擅自变更模型**：模型名称、endpoint、API Key 全部从环境变量/配置读取，代码中不硬编码。
4. **防御式序列化**：AI 输出可能缺字段，后端用 `.get()` + 默认值兜底，不让 KeyError 冒泡到前端。

## 三、数据库实体及关系设计

### 3.1 ER 总览

```
subject_field_templates ──(定义字段)──> subjects <──(source)── relationships ──(target)──> subjects
                                           ▲                        ▲
                                           │                        │
                                     extraction_results       relationship_types
                                           ▲
                                           │
                                     extraction_tasks
                                           ▲
                                           │
                                     data_sources
```

### 3.2 表结构详细设计

#### 3.2.1 `subjects`（主体表 — 个人+组织统一）

采用 **核心字段列 + 扩展字段 JSONB** 的混合模式：核心查询字段单独列（便于索引和搜索），其他业务字段放 `extra` JSONB。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID PK | 主键 |
| `type` | VARCHAR(10) | `person` / `org`，NOT NULL |
| `name` | VARCHAR(200) | 姓名或组织名称，NOT NULL，建索引 |
| `phone` | VARCHAR(50) | 手机号，可空，建索引 |
| `email` | VARCHAR(200) | 邮箱，可空 |
| `id_card` | VARCHAR(50) | 身份证号（仅个人），可空 |
| `org_code` | VARCHAR(50) | 统一社会信用代码（仅组织），可空 |
| `tags` | TEXT[] | 标签数组 |
| `extra` | JSONB | 扩展字段，按字段模板存储 |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 更新时间 |

**索引**：`(type, name)` 联合索引、`phone` 索引、`name` 模糊搜索用 `pg_trgm`。

#### 3.2.2 `subject_field_templates`（字段模板表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID PK | |
| `subject_type` | VARCHAR(10) | `person` / `org` |
| `field_key` | VARCHAR(50) | 字段标识，如 `gender`、`industry` |
| `field_name` | VARCHAR(100) | 显示名称，如 "性别"、"所属行业" |
| `field_type` | VARCHAR(20) | `text` / `number` / `date` / `select` / `multi_select` |
| `required` | BOOLEAN | 是否必填 |
| `options` | JSONB | 下拉选项（select 类型用） |
| `sort_order` | INT | 排序 |

**P0 预置模板**：

个人模板：姓名*、性别、出生日期、手机号、邮箱、身份证号、所在城市、职业、备注

组织模板：名称*、统一社会信用代码、行业、规模、所在城市、联系电话、官网、备注

#### 3.2.3 `relationships`（关系表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID PK | |
| `source_subject_id` | UUID FK | 关系起点主体 |
| `target_subject_id` | UUID FK | 关系终点主体 |
| `rel_type` | VARCHAR(50) | 关系类型枚举（见 3.2.4） |
| `description` | TEXT | 关系描述，可空 |
| `created_at` | TIMESTAMPTZ | |

**约束**：`source_subject_id != target_subject_id`（禁止自环）；`(source, target, rel_type)` 联合唯一。

#### 3.2.4 `relationship_types`（关系类型字典）

P0 内置，不开放增删改 UI。

| 关系类型 | 方向 | 适用主体组合 |
|---------|------|------------|
| `works_at` | 单向 | 个人 → 组织（任职于） |
| `member_of` | 单向 | 个人/组织 → 组织（隶属于） |
| `founded` | 单向 | 个人 → 组织（创立了） |
| `knows` | 双向 | 个人 ↔ 个人（认识） |
| `colleague_of` | 双向 | 个人 ↔ 个人（同事） |
| `family_of` | 双向 | 个人 ↔ 个人（家属） |
| `cooperates_with` | 双向 | 组织 ↔ 组织（合作） |

**方向说明**：双向关系在入库时自动写两条记录（A→B 和 B→A），保证查询任一方向都能命中。

#### 3.2.5 `data_sources`（数据源表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID PK | |
| `file_type` | VARCHAR(20) | `excel` / `chat` |
| `file_name` | VARCHAR(255) | 原始文件名 |
| `file_path` | VARCHAR(500) | 服务器存储路径 |
| `file_size` | BIGINT | 字节数 |
| `status` | VARCHAR(20) | `uploaded` / `parsing` / `parsed` / `failed` |
| `parsed_text` | TEXT | 解析后的纯文本（聊天记录直接存，Excel 转文本） |
| `created_at` | TIMESTAMPTZ | |

#### 3.2.6 `extraction_tasks`（抽取任务表）

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID PK | |
| `data_source_id` | UUID FK | 关联数据源 |
| `status` | VARCHAR(20) | `pending` / `processing` / `completed` / `failed` |
| `ai_model` | VARCHAR(100) | 使用的模型名（从配置读取） |
| `prompt_version` | VARCHAR(20) | Prompt 版本号 |
| `error_msg` | TEXT | 失败原因 |
| `created_at` | TIMESTAMPTZ | |
| `completed_at` | TIMESTAMPTZ | |

#### 3.2.7 `extraction_results`（抽取结果表 — 审核前的候选数据）

这是**核心中间表**，AI 提取的候选主体和关系都存在这里，审核通过后才写入正式表。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | UUID PK | |
| `task_id` | UUID FK | |
| `candidate_subjects` | JSONB | 候选主体数组（结构见 3.3） |
| `candidate_relationships` | JSONB | 候选关系数组（结构见 3.3） |
| `dedup_result` | JSONB | 去重匹配结果（每个候选标注 match_type） |
| `review_status` | VARCHAR(20) | `pending` / `approved` / `rejected` |
| `review_note` | TEXT | 审核备注 |
| `reviewed_at` | TIMESTAMPTZ | |

### 3.3 AI 输出 JSON Schema（全链路契约）

```json
{
  "subjects": [
    {
      "type": "person",
      "name": "张三",
      "phone": "13800138000",
      "email": null,
      "id_card": null,
      "org_code": null,
      "extra": {
        "gender": "男",
        "city": "北京"
      }
    }
  ],
  "relationships": [
    {
      "source_name": "张三",
      "target_name": "某某公益组织",
      "rel_type": "works_at",
      "description": "担任项目主管"
    }
  ]
}
```

> **关键约束**：`source_name` / `target_name` 必须与 `subjects[].name` 完全一致，后端用名称做临时关联，去重匹配后替换为主体 ID。

### 3.4 去重匹配策略

对每个候选主体，与库内已有主体比对，输出 `match_type`：

| match_type | 含义 | 处理方式 |
|-----------|------|---------|
| `new` | 无匹配 | 审核通过后新建 |
| `exact` | 精确匹配（姓名+手机 或 姓名+身份证 或 名称+信用代码） | 审核通过后更新已有主体 |
| `likely` | 高概率匹配（姓名相同+城市相同，或手机号相同） | 审核时人工确认 |
| `unlikely` | 低概率匹配（仅姓名相同） | 默认按新建处理，审核时可改 |

**匹配规则优先级**（从高到低）：
1. 身份证号 / 统一社会信用代码完全相同 → `exact`
2. 手机号完全相同 + 姓名相同 → `exact`
3. 邮箱完全相同 + 姓名相同 → `likely`
4. 姓名完全相同 + 城市相同 → `likely`
5. 姓名完全相同 → `unlikely`
6. 其他 → `new`

## 四、前后端接口设计

### 4.1 接口规范

- Base URL：`/api`
- 请求/响应：JSON（文件上传除外，用 `multipart/form-data`）
- 分页参数：`page`（从 1 开始）、`page_size`（默认 20）
- 统一响应格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 4.2 主体管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/subjects` | 主体列表，支持 `type`、`keyword`、`tag` 筛选 + 分页 |
| GET | `/api/subjects/{id}` | 主体详情（含字段值 + 关系列表） |
| POST | `/api/subjects` | 手动创建主体 |
| PUT | `/api/subjects/{id}` | 更新主体 |
| DELETE | `/api/subjects/{id}` | 删除主体（同时删除其关系） |
| GET | `/api/subjects/{id}/network` | 主体关系网络（1~2 度关系，用于图谱） |

### 4.3 字段模板

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/field-templates` | 查询模板，参数 `subject_type=person|org` |
| PUT | `/api/field-templates/{id}` | 更新单个字段配置（P0 仅改 required/options） |

### 4.4 关系管理

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/relationships` | 按 `subject_id` 查询某主体的所有关系 |
| POST | `/api/relationships` | 创建关系（双向关系自动写两条） |
| DELETE | `/api/relationships/{id}` | 删除关系（双向关系同时删反向） |
| GET | `/api/relationship-types` | 关系类型字典 |

### 4.5 数据上传与解析

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/data-sources/upload` | 上传文件，`file` 字段 + `file_type` 参数 |
| GET | `/api/data-sources` | 数据源列表 |
| GET | `/api/data-sources/{id}` | 数据源详情（含解析后的文本预览） |
| DELETE | `/api/data-sources/{id}` | 删除数据源 |

**Excel 解析规则**（P0 简化版）：
- 要求 Excel 第一行为表头，列名需包含 `姓名`/`名称`（必选），其他列名尽量与字段模板 `field_name` 对应
- 解析后将每一行转为 JSON 对象，拼接到 `parsed_text`（用结构化文本格式，便于 AI 识别）

**聊天记录解析规则**（P0）：
- 支持 `.txt` 格式，按行读取
- 直接存入 `parsed_text`，由 AI 自行识别对话中的人物和关系

### 4.6 AI 抽取与审核

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/extraction-tasks` | 创建抽取任务（传入 `data_source_id`） |
| GET | `/api/extraction-tasks/{id}` | 查询任务状态 |
| GET | `/api/extraction-tasks/{id}/results` | 获取抽取结果（含去重匹配标注） |
| POST | `/api/extraction-tasks/{id}/review` | 提交审核结果（通过/修改/拒绝） |
| POST | `/api/extraction-tasks/{id}/re-extract` | 重新提取（Prompt 调整后重跑） |

**审核提交结构**：

```json
{
  "decision": "approved",
  "subject_overrides": {
    "<candidate_index>": {
      "match_type": "exact",
      "matched_subject_id": "uuid"
    }
  },
  "rejected_subject_indexes": [2, 5],
  "note": "已确认"
}
```

### 4.7 主体画像

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/subjects/{id}/profile` | 主体画像（基本信息 + 关系统计 + 来源） |

## 六、实现难点与潜在风险

### 6.1 实现难点

#### 难点 1：AI 输出的稳定性与一致性

**问题**：大模型输出的 JSON 可能缺字段、类型错误、`source_name` 与 `subjects` 对不上。

**应对**：
- Prompt 中给出完整 JSON Schema 示例，要求严格按格式输出
- 后端用 Pydantic 模型校验，校验失败自动重试（最多 3 次，重试时附错误信息）
- 用 `json_repair` 库修复截断/不完整的 JSON
- 对 `source_name`/`target_name` 做归一化（去空格、大小写）后再匹配

#### 难点 2：去重匹配的准确率

**问题**：同名不同人、同人不同名（别名/英文名）、手机号缺失等情况会导致误判。

**应对**：
- P0 阶段采用保守策略：宁可标 `likely` 让人工确认，也不自动合并
- 提供"审核时修改匹配结果"的能力，人工可将 `likely` 改为 `new` 或指定已有主体
- 不在 P0 做复杂的模糊匹配算法（如编辑距离），只用精确字段比对

#### 难点 3：Excel 列名与系统字段的映射

**问题**：用户上传的 Excel 列名五花八门，无法直接对应系统字段。

**应对**：
- P0 提供模板下载功能，要求用户按模板格式填写
- 解析时做关键词模糊匹配列名（如 "手机"/"电话"/"联系方式" → `phone`）
- 无法匹配的列放入 `extra` 的"未映射字段"中，审核时人工处理

#### 难点 4：异步任务的状态管理

**问题**：AI 提取耗时较长（可能 30s~数分钟），需要异步处理。

**应对**：
- P0 用 FastAPI `BackgroundTasks`，不引入 Celery/Redis
- 任务状态存在数据库，前端轮询（每 3s 查一次）
- 若任务量大再评估引入任务队列

### 6.2 潜在风险

| 风险 | 影响 | 等级 | 应对措施 |
|------|------|------|---------|
| AI 模型输出不稳定 | 抽取失败率高 | 高 | JSON 校验 + 重试 + 错误提示 |
| 去重误合并 | 数据污染 | 高 | 保守策略 + 人工确认 + 不自动合并 |
| Excel 格式不统一 | 解析失败 | 中 | 提供模板 + 列名模糊匹配 |
| 大批量上传内存溢出 | 服务崩溃 | 中 | 限制单次上传大小（P0 限 10MB），流式解析 |
| 双向关系数据不一致 | 查询遗漏 | 中 | 入库时用事务保证两条同时写入 |
| 图谱节点过多卡顿 | 前端卡死 | 低 | P0 只查 1~2 度关系，限制节点数 ≤ 100 |
| 模型 API Key 泄露 | 安全问题 | 中 | Key 存环境变量，不进代码仓库 |
